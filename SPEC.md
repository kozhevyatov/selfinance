# Selfinance — спецификация

Self-hosted сервис учёта доходов и расходов. Работает в Docker, фронтенд на React, бэкенд отдаёт REST API (на нём же позже будут Android/iOS приложения).

Принцип: **просто по умолчанию, мощно по желанию.** Чтобы записать операцию, достаточно ввести сумму. Счета, категории, заморозка и семейные бюджеты включаются, только когда они нужны.

| Бэкенд | Node.js 22 + Fastify | Быстрый, простой, генерирует OpenAPI |
| Запросы / миграции | Kysely | Один код запросов и миграций для SQLite и MySQL/MariaDB (Drizzle требует отдельные схемы на каждую СУБД) |

| Авторизация | JWT access (15 мин) + refresh (30 дней, ротация), пароли argon2 | Подходит и для веба, и для мобильных приложений |
| Фронтенд | React + Vite + React Router + TanStack Query | |
| Графики | Recharts | |
| Мобилка (позже) | Expo (React Native) | Переиспользует `packages/shared` |
| Документация API | Swagger UI на `/api/docs` | |

### Соглашения по данным
- **Суммы хранятся целыми числами в копейках** (`amount: integer`, всегда > 0). Знак операции определяет её тип, а не число.
- **ID — UUID v7** (сортируются по времени). Нужны для будущей офлайн-синхронизации мобилки.
- У всех сущностей есть `created_at`, `updated_at`, `deleted_at` (мягкое удаление).
- Даты операций хранятся как `date` (без времени) плюс необязательное `time`. Часовой пояс задаётся в настройках пользователя.
- Валюта пока одна (₽). У бюджета есть поле `currency` на будущее, в интерфейсе не выводится.

## 3. Первый запуск (мастер настройки)

Если `data/config.json` не существует, приложение открывает мастер:

1. **База данных:** SQLite (по умолчанию) или внешняя MySQL/MariaDB (хост, порт, БД, логин, пароль) с кнопкой «Проверить подключение».
2. **Администратор:** имя, email и/или телефон, пароль.
3. **Регистрация:** открытая / только по приглашениям / закрытая.

После завершения применяются миграции, создаётся админ и его личный бюджет. Мастер больше не показывается.

## 4. Пользователи и роли

- **Админ сервиса:** управляет пользователями (создать, заблокировать, сбросить пароль), режимом регистрации и приглашениями. Чужие финансы **не видит**.
- **Пользователь:** работает со своими бюджетами.
- **Вход по email или по телефону.**
  - Оба поля уникальные. При регистрации обязательно хотя бы одно из них, второе можно добавить позже в профиле.
  - На экране входа одно поле «Email или телефон». Сервер сам определяет, что введено: если есть `@`, это email.
  - Телефон нормализуется в формат E.164 (`+79991234567`), поэтому «8 999…», «+7 (999)…» и «9991234567» считаются одним номером. Email хранится в нижнем регистре.
  - Восстановление пароля: по email, если на сервере настроен SMTP (необязательно). Иначе пароль сбрасывает админ. SMS не используем.
- Режимы регистрации:
  - `open` — может зарегистрироваться любой;
  - `invite` — только по ссылке-приглашению от админа;
  - `closed` — пользователей заводит только админ.

## 5. Бюджеты: личный и семейный

**Бюджет** — это контейнер, в котором живут счета, категории и операции. Всё остальное в модели принадлежит какому-то бюджету.

- При регистрации у каждого пользователя автоматически создаётся **«Личный»** бюджет.
- Любой пользователь может создать **общий бюджет** (например, «Семья») и пригласить в него других пользователей сервиса.
- Роли участника общего бюджета:
  - **владелец** — всё, включая приглашение и удаление участников и удаление бюджета;
  - **участник** — добавляет и редактирует операции, счета и категории;
  - **наблюдатель** — только просмотр (например, для ребёнка или бухгалтера).
- В общем бюджете у каждой операции видно, **кто её добавил**. В статистике есть фильтр и разбивка «по участникам».
- Личный бюджет другие пользователи не видят никогда.
- **Переключатель бюджета** в шапке. Если у пользователя только личный бюджет, переключатель скрыт и интерфейс выглядит как обычный личный учёт.

### Перевод между бюджетами
Например, «скинул 20 000 со своей карты в семейный бюджет».

- Это одна операция, которая порождает **две связанные записи**: уход денег со счёта в одном бюджете и поступление на счёт в другом. Записи связаны через `transfer_group_id`; удаление или редактирование одной меняет обе.
- В статистике такие суммы **не попадают в расходы и доходы по категориям**. Они показываются отдельной строкой: «Передано в другие бюджеты» / «Получено из других бюджетов».

## 6. Модель данных

```
users             id, email? (unique), phone? (unique, E.164), name, password_hash, is_admin, is_blocked, timezone, created_at…
refresh_tokens    id, user_id, token_hash, device_name, expires_at, revoked_at
invites           id, code, created_by, expires_at, used_by, used_at
settings          key, value                      (режим регистрации и т. п.)

budgets           id, name, type ('personal'|'shared'), currency, created_by, …
budget_members    budget_id, user_id, role ('owner'|'member'|'viewer'), joined_at
budget_invites    id, budget_id, code, role, created_by, expires_at, used_by

accounts          id, budget_id, name, kind, is_frozen, parent_account_id?, bank_name?,
                  color, icon, sort, is_archived, note, …
categories        id, budget_id, parent_id?, type ('income'|'expense'), name, color, icon, sort, is_archived
transactions      id, budget_id, type, amount, date, time?, account_id, to_account_id?,
                  category_id?, comment, created_by, transfer_group_id?, …
```

### Счета (`accounts`)
- `kind`: `cash` (наличные), `bank` (банковский счёт или карта), `deposit` (вклад), `savings` (накопления, копилка).
- `is_frozen`: если `true`, деньги на счёте **заморожены** и не входят в «оборот». Для `deposit` и `savings` по умолчанию `true`, но флаг можно поменять у любого счёта.
- `bank_name`: свободное текстовое поле. Счета одного банка группируются в интерфейсе.
- `parent_account_id` (необязательно): копилка «внутри» карты, например «Сбер карта → Отпуск».
- Баланс **не хранится**, он вычисляется из операций. Поэтому любое редактирование прошлого корректно пересчитывает остатки.
- Счёт с историей не удаляется, а архивируется.

### Операции (`transactions`)

| type | Поля | Влияние на баланс | В статистике доходов/расходов |
|---|---|---|---|
| `income` | account_id, category_id? | +amount на счёт | доход |
| `expense` | account_id, category_id? | −amount со счёта | расход |
| `transfer` | account_id → to_account_id | перенос | **не учитывается** |
| `adjustment` | account_id, amount со знаком | ± | не учитывается (отдельная строка «корректировки») |

- **Заморозка** — это `transfer` со счёта «в обороте» на счёт «заморожено». **Разморозка** — обратный перевод. В интерфейсе это кнопки «Заморозить» и «Разморозить» на экране счетов, под капотом обычный перевод.
- **Снять наличные / положить на карту / перекинуть между банками** — тоже `transfer`.
- **Начальный остаток** при создании счёта сохраняется как `adjustment` с комментарием «Начальный остаток».
- **Сверка баланса:** пользователь вводит фактический остаток, система создаёт `adjustment` на разницу.
- Без категории операция попадает в виртуальную группу «Без категории».

### Категории
- Два уровня: категория → подкатегория (`parent_id`). Глубже не делаем.
- Отдельные деревья для доходов и для расходов.
- Операцию можно отнести к категории целиком или к конкретной подкатегории. Статистика суммирует подкатегории в родителя.
- При создании бюджета предлагается стартовый набор, который можно удалить:
  - **Расходы:** Продукты, Кафе и рестораны, Транспорт, Машина (Бензин, ТО и ремонт, Страховка, Парковка и штрафы, Мойка), Дом и ЖКХ, Связь и интернет, Здоровье, Одежда, Развлечения, Подарки, Подписки, Прочее.
  - **Доходы:** Зарплата, Подработка, Подарки, Проценты и кэшбэк, Прочее.

## 7. Режим «просто доход/расход»

- В новом бюджете автоматически создаётся один счёт **«Кошелёк»** (`cash`, в обороте).
- Пока в бюджете один счёт, поле «Счёт» в формах **не показывается**, а на главной нет блока счетов.
- Категория необязательна.
- В итоге минимальная запись выглядит так: сумма → «Расход» → готово.

## 7a. Регулярные платежи и напоминания

Нужны для платежей, которые повторяются каждый месяц: ЖКХ, связь, подписки, кредит, аренда.

**Как отметить платёж:**
- В форме операции есть переключатель **«Регулярный»**. Его можно включить при создании или позже, при редактировании.
- При включении создаётся правило регулярного платежа. Название, категория, счёт и сумма берутся из операции. День месяца берётся из её даты.

**Дата следующего платежа:**
- Это **день последнего фактического платежа**, перенесённый на следующий месяц.
- Если последний платёж был 31-го, а в следующем месяце 30 дней, платёж ожидается в последний день месяца.
- Если оплатил позже обычного, дальше напоминание сдвигается на новый день. В правиле можно вручную **закрепить день**, тогда сдвига не будет.

**Сумма:** берётся из последнего платежа. Если суммы плавают (как у ЖКХ), перед ней ставится «≈».

**Напоминание на главной:**
- Плашка «Скоро платежи» появляется за **3 дня** до даты. Срок настраивается: 1–7 дней.
- В плашке видно название, дату («через 2 дня», «завтра», «сегодня») и сумму.
- Если дата прошла, а платежа нет, он становится красным и помечается «просрочен».
- Кнопки:
  - **«Оплатить»** — открывает форму с заполненными полями. Достаточно проверить сумму и сохранить.
  - **«Пропустить»** — только в этом месяце.
- Плашка закрывается сама, если операция внесена как оплата этого правила. Также предлагается связать с правилом подходящую операцию (та же категория, ±5 дней), если она внесена вручную.

**Раздел «Регулярные»** находится в настройках или на экране операций. В нём:
- список правил с ближайшими датами;
- сумма регулярных платежей в месяц;
- пауза, редактирование, удаление.

**Модель:**
```
recurring         id, budget_id, name, type ('expense'|'income'), category_id?, account_id?,
                  amount (последняя), amount_varies (bool), day_of_month, day_pinned (bool),
                  remind_days (default 3), is_paused, last_paid_date, …
transactions      + recurring_id?           связь операции с правилом
recurring_skips   recurring_id, month       «пропустить в этом месяце»
```

**API:**
- `GET|POST|PATCH|DELETE /budgets/{id}/recurring`;
- `GET /budgets/{id}/recurring/upcoming?days=7` — для плашки;
- `POST /budgets/{id}/recurring/{rid}/skip`.

**Потом:**
- push-уведомления в мобильном приложении;
- другие периоды: раз в неделю, раз в квартал, раз в год (страховка, налоги).

## 7b. Лимит расходов

**Общий лимит на месяц**, например 50 000 ₽. Задаётся один раз и действует каждый месяц, пока его не изменить. Изменение действует с текущего месяца, у прошлых сохраняются их лимиты (таблица `limits` хранит значение и месяц, с которого оно действует).

**Что считается в лимит:**
- все расходы месяца, **кроме обязательных платежей** — операций, привязанных к регулярным платежам (раздел 7a). Переключатель «Учитывать обязательные платежи» в настройках лимита, по умолчанию выключен;
- кроме категорий с отметкой «Не учитывать в лимите» (вместе с подкатегориями), например «Ремонт» или «Лечение».

**Карточка на главной:**
- полоса «потрачено / лимит» с меткой прогноза на конец месяца;
- цвета: обычный, жёлтый (потрачено 80% или прогноз превышает лимит), красный (лимит превышен);
- «Потрачено X, осталось Y»;
- «До конца месяца N дней, можно тратить ≈ Z ₽ в день» — главная подсказка, пересчитывается каждый день;
- «При таком темпе выйдет ≈ … — на … больше лимита»;
- «Обязательные платежи отдельно: … (оплачено …, впереди …)»;
- для прошлых месяцев: уложились или превысили.

**Лимиты по категориям (по желанию):** например «Кафе — 8 000 ₽». Считаются все расходы категории с подкатегориями. В блоке «Куда ушли деньги» у такой категории шкала «X из лимита».

**Модель:**
```
limits            id, budget_id, category_id? (null — общий), amount (0 — снять лимит), from_month
categories        + exclude_from_limit
budgets           + limit_include_recurring
```

**API:**
- `GET /budgets/{id}/limits?month=` — статус на месяц;
- `PUT /budgets/{id}/limits { categoryId?, amount, fromMonth }`;
- `PATCH /budgets/{id}/limit-settings { includeRecurring }`.

**Потом:** push-уведомления при 80% и 100% (в мобильном приложении).

## 7c. Запланированные расходы

Заметка о будущей покупке: «через 10 дней купить зимнюю резину за 30 000». Висит на главной, пока не куплено или не отменено, и показывает, хватает ли на неё денег.

**План:**
- название, сумма;
- дата — **необязательна**. Без даты это вишлист: «когда-нибудь купить»;
- категория, комментарий, счёт для оплаты — по желанию;
- «Не учитывать в лимите» — по умолчанию **включено**: покупка запланирована заранее, это не импульсная трата.

**Сколько не хватает (прогноз):**
- База — **свободные деньги** (счета в обороте, без замороженных).
- Планы с датой и **регулярные расходы**, которые наступят до даты последнего плана, выстраиваются по дате. Идёт нарастающий итог: из свободных денег по очереди вычитается каждая трата.
- У каждого плана: «хватает» или «не хватает X» — насколько в этот момент нарастающий остаток уходит в минус.
- Ожидаемые доходы (регулярная зарплата) **не прибавляются**: прогноз осторожный.
- Просроченные планы считаются как сегодняшние.
- На карточке «Свободные деньги» строка **«После планов: X ₽»** (красная, если минус). По нажатию — расшифровка: `Свободно 40 000 − ЖКХ ≈7 000 − Интернет 800 − Резина 30 000 = −2 200`.
- **Планы без даты** в нарастающий итог не входят. У каждого подсказка: «можно купить сейчас» или «не хватает X» относительно остатка после всех датированных планов.

**Отложить под план:**
- Кнопка «Отложить» переводит сумму со счёта в обороте на замороженную копилку этого плана. Копилка — обычный счёт (`savings`, заморожен), создаётся при первом откладывании, родитель — счёт, с которого отложили.
- Откладывать можно частями. У плана полоса «отложено X из Y»; в прогнозе учитывается только неотложенный остаток.
- «Вернуть» — перевод обратно на счёт (разморозка).

**Выполнение:**
- **«Купил»** открывает форму расхода с заполненными полями; сумму можно поправить. Операция связывается с планом (`planned_id`), план переходит в «выполненные».
- Если под план было отложено, отложенное автоматически возвращается на счёт покупки, а копилка архивируется.
- **«Перенести»** — сменить дату. **«Отменить»** — план в архив, отложенное возвращается на счёт.
- Дата прошла, а покупки нет — план красный, «просрочен».
- Удаление операции покупки возвращает план в активные.

**Где видно:**
- На главной панель **«Впереди»**: регулярные платежи (как раньше, за N дней) и все активные планы, по дате; планы без даты — внизу.
- Экран **«Планы»**: активные с прогнозом, ниже выполненные и отменённые.

**Модель:**
```
planned           id, budget_id, name, amount, date?, category_id?, account_id?, comment,
                  status ('active'|'done'|'cancelled'), exclude_from_limit (default 1),
                  reserve_account_id?, transaction_id?, done_at?, created_by, …
transactions      + planned_id?
```

**API:**
- `GET /budgets/{id}/planned` — активные планы с прогнозом + история;
- `POST|PATCH|DELETE /budgets/{id}/planned/{pid}`;
- `POST /budgets/{id}/planned/{pid}/reserve { amount, fromAccountId }`;
- `POST /budgets/{id}/planned/{pid}/release { amount?, toAccountId? }`;
- `POST /budgets/{id}/planned/{pid}/cancel`;
- покупка — обычный `POST /transactions` с `plannedId`.

## 8. Статистика

Период: месяц (по умолчанию текущий; стрелки ← →), неделя, год или произвольный диапазон.

**Итоги периода:**
- Приход, Расход, Разница (приход − расход).
- Сравнение с предыдущим аналогичным периодом: ▲/▼ в % и рублях.
- **Средний расход в день**: расход / число дней. Для текущего месяца берутся прошедшие дни, включая сегодня.
- **Средний расход в неделю** = средний в день × 7.
- Прогноз на конец текущего месяца: средний в день × число дней в месяце.

**Динамика:**
- Столбцы приход/расход по месяцам за последние 12 месяцев (или по дням внутри выбранного месяца).
- Линия общего капитала (в обороте + заморожено) на конец каждого месяца.

**Структура:**
- Бублик расходов (и отдельно доходов) по категориям. Клик по сектору раскрывает подкатегории.
- Таблица категорий: сумма, % от общего, изменение к прошлому периоду.

**Капитал (на текущий момент):**
- **В обороте**: сумма по счетам с `is_frozen = false`.
- **Заморожено**: сумма по счетам с `is_frozen = true`.
- **Всего.**
- Разбивка по счетам и банкам.

**Фильтры:** счёт, категория, участник (в общем бюджете).

Переводы и корректировки в доходы и расходы не входят. Корректировки и переводы между бюджетами показываются отдельными строками, чтобы итог сходился с балансом.

## 9. Экраны веб-приложения

1. **Главная.** Карточки «В обороте / Заморожено / Всего» и строка «После планов»; панель «Впереди» (регулярные платежи в ближайшие дни и запланированные расходы); итоги текущего месяца (приход, расход, разница, средний в день); последние 10 операций; плавающая кнопка **«+»**.
2. **Добавление и редактирование операции** (модальное окно или bottom sheet на мобильном):
   - сумма (автофокус; можно писать выражения вроде `350+120`);
   - тип: Расход (по умолчанию) / Доход / Перевод;
   - категория (сетка иконок; поиск; подкатегории раскрываются);
   - счёт (по умолчанию последний использованный; скрыт, если счёт один);
   - для перевода «откуда → куда»;
   - дата (по умолчанию сегодня; быстрые кнопки «вчера» и «позавчера»);
   - комментарий.
3. **Операции.** Лента по дням с дневными итогами; фильтры (период, тип, счёт, категория, участник, поиск по комментарию); редактирование по клику; удаление.
4. **Статистика.** См. раздел 8.
5. **Счета.** Группы «В обороте» и «Заморожено», внутри по банкам. Остаток каждого счёта. Действия: перевод, заморозить, разморозить, сверить баланс, редактировать, архивировать.
6. **Категории.** Дерево с drag-and-drop сортировкой, иконки, цвета, архив.
7. **Бюджеты.** Список; создание общего; участники и роли; приглашения по ссылке.
8. **Настройки.** Профиль, пароль, часовой пояс, первый день недели, тема (светлая/тёмная), активные сессии и устройства.
9. **Админка.** Пользователи, режим регистрации, приглашения, информация о сервисе (версия, тип БД).

Интерфейс адаптивный, на мобильном нижняя навигация. Работает как PWA (можно «установить» на телефон ещё до нативных приложений).

### Дизайн
Стиль: спокойное современное финтех-приложение. Много воздуха, крупные цифры, минимум декора. Цвет используется как смысл, а не как украшение.

- **Темы:** светлая и тёмная, по умолчанию следует системной.
- **Основа:**
  - светлая тема: фон `#F2F3F5`, карточки белые;
  - тёмная тема: фон `#0F1115`, карточки `#181B21`;
  - текст: графит или почти белый.
- **Акцент:** глубокий индиго `#4338CA` (тёмная тема: `#8B8CF8`). Это кнопки, активные элементы и «+». Нейтральный цвет, который не путается с доходами и расходами.
- **Смысловые цвета** одинаковы во всём приложении:
  - доход — зелёный `#15803D`;
  - расход — коралловый `#D9434A`;
  - заморожено — ледяной голубой `#0E9AD6` (иконка снежинки, штриховка «лёд» на полосе капитала);
  - перевод — серый.
- **Шрифт:** Onest (хорошая кириллица; в сборке подключается локально через @fontsource), запасной — Inter. Для сумм используются табличные цифры, чтобы колонки ровно выравнивались. Суммы форматируются как `12 345,67 ₽`, копейки визуально приглушены.
- **Карточки:** скругление 22px (панели) / 14px (элементы), лёгкая тень в светлой теме, тонкая обводка в тёмной.
- **Категории:** у каждой цветная иконка в кружке, набор Lucide.
- **Мобильный вид:**
  - нижняя панель с разделами Главная / Операции / «+» / Статистика / Счета;
  - формы открываются снизу (bottom sheet);
  - крупные зоны нажатия, от 44px;
  - числовая клавиатура для суммы.
- **Десктоп:** боковое меню, контент шириной до ~1200px. Статистика выводится в две колонки: графики и таблица.

## 10. API (основное)

Все маршруты под `/api/v1`. Операции с данными бюджета идут под `/budgets/{budgetId}/…`, права проверяются по `budget_members`.

```
POST   /setup                         мастер первого запуска (только пока нет config)
GET    /setup/status

POST   /auth/register | /auth/login | /auth/refresh | /auth/logout
GET    /auth/me        PATCH /auth/me

GET    /budgets                      POST /budgets
PATCH  /budgets/{id}                 DELETE /budgets/{id}
GET    /budgets/{id}/members         PATCH|DELETE /budgets/{id}/members/{userId}
POST   /budgets/{id}/invites         POST /budget-invites/{code}/accept

GET|POST            /budgets/{id}/accounts
PATCH|DELETE        /budgets/{id}/accounts/{accId}
POST                /budgets/{id}/accounts/{accId}/reconcile   { actualBalance }

GET|POST            /budgets/{id}/categories
PATCH|DELETE        /budgets/{id}/categories/{catId}

GET                 /budgets/{id}/transactions?from&to&type&account&category&user&q&cursor
POST                /budgets/{id}/transactions
PATCH|DELETE        /budgets/{id}/transactions/{txId}
POST                /transfers/cross-budget      перевод между бюджетами

GET    /budgets/{id}/stats/summary?from&to        итоги, средние, сравнение
GET    /budgets/{id}/stats/dynamics?from&to&step=day|month
GET    /budgets/{id}/stats/categories?from&to&type
GET    /budgets/{id}/stats/capital               в обороте / заморожено / по счетам

GET|POST|PATCH  /admin/users …       GET|PATCH /admin/settings     /admin/invites
GET    /health
```

- Пагинация курсорная.
- Ошибки в едином формате `{ error: { code, message, fields? } }`.
- Для будущей синхронизации мобилки: `GET /budgets/{id}/changes?since=<timestamp>` (заложить в модель сейчас, реализовать позже).

## 11. Этапы

**v1 (MVP):**
- мастер настройки (SQLite / MariaDB);
- регистрация, роли, админка;
- личный бюджет: операции (доход, расход, перевод, корректировка), счета с заморозкой, категории с подкатегориями;
- главная, лента операций, статистика (итоги, средние, динамика, структура, капитал);
- регулярные платежи с напоминаниями на главной (раздел 7a);
- лимит расходов на месяц и по категориям (раздел 7b);
- запланированные расходы с прогнозом нехватки и «отложить» (раздел 7c);
- адаптивный интерфейс и PWA;
- Docker и деплой.

**v1.1:**
- общие (семейные) бюджеты, приглашения, роли участников;
- переводы между бюджетами.

Модель с `budget_id` закладывается **сразу в v1**, поэтому общие бюджеты добавятся без миграций данных.

**Потом (по желанию):**
- регулярные платежи с другими периодами (неделя, квартал, год) и push-уведомления;
- цели накоплений на замороженных счетах;
- долги;
- фото чеков;
- подсказка категории по комментарию;
- мультивалютность;
- мобильные приложения на Expo с офлайн-синхронизацией.
